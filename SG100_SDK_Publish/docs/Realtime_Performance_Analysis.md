# SG100 SDK 运行逻辑、实时性与问题分析

## 1. 结论

当前 RS485 主动模式的控制周期被固定为 **10 ms（100 Hz）**，一次周期按“发送 -> 固定等待 5 ms -> 轮询接收 -> 等待下一个 10 ms 时刻”串行执行。因此：

- 应用层更快地调用 `SetJointPosition()` 不会产生同等频率的总线帧，只会反复覆盖线程安全的控制缓存；后台线程在下一周期读取最新值。
- 在不改协议和掌板固件的前提下，可以通过消除固定等待、及时收包、参数化周期、改善调度方式来降低数毫秒级主机延迟和抖动。
- 若目标只是稳定的 100 Hz，**不必推翻程序框架**；保留设备层、协议层、适配器层，重点重构 `CommScheduler` 和 RS485 接收机制即可。
- 若目标是可靠的 200 Hz、500 Hz 或 1 kHz 闭环交互，则必须同时核对串口带宽、掌板处理周期、掌板到 11 个关节的总线周期及固件协议，不能只修改 PC 线程的 `sleep`。

## 2. SDK 实际运行链路

### 2.1 初始化与对象关系

1. `SG100DeviceManager::AddDevice()` 创建 `SG100Device`，加载串口配置并打开 RS485 适配器。
2. `SG100Device::Impl` 持有：
   - `RS485Adapter` / `CANFDAdapter`：物理传输与收发缓存；
   - `SG100Protocol`：帧打包；
   - `ProtocolHandler`：响应分发、状态缓存和用户回调；
   - `CommScheduler`：命令队列与 RS485 后台调度线程。
3. `StartAll()` 启动每个主动式 RS485 设备的 `CommScheduler::SerialTask()`。CAN FD 被动模式不启动该线程，由外部循环取发帧、注入收帧。

### 2.2 实时模式

应用调用 `SetHandControl()`、`SetJointPosition()` 或 `SetJointPositions()` 时，只更新 `cached_control_`。后台线程每 10 ms 执行一次：

1. 若实时命令 FIFO 非空，取出一个队列命令；否则复制并编码最新的 `cached_control_`，生成 `CMD_REALTIME_CTRL (0x05)` 整手帧。
2. `SG100Protocol::Pack()` 生成协议头和载荷，`RS485Adapter::Send()` 追加 CRC32 后写串口。
3. 固定休眠 5 ms。
4. `PollReceive()` 查询串口当前可读字节，校验、拆帧，并交给 `ProtocolHandler::HandleFrame()`。
5. 整手状态写入带锁缓存，随后在同一个通信线程中同步调用用户状态回调。

控制缓存保存用户角度（degree）；真正发帧前按 `joint_angle_map.json` 做方向、偏置、限位映射，再转换为弧度。收到状态时执行逆映射，所以 `GetCachedPosition()` 返回用户角度。

### 2.3 透传模式

透传模式不自动发送整手控制帧，只以每 10 ms 最多一条的速度处理 `passthrough_queue_`。参数读写、标定、FOC 使能和关节级命令主要通过此路径执行。模式切换会停止后台线程，由调用线程独占串口发送切换命令并轮询 ACK，之后重新启动调度线程。

### 2.4 示例程序的典型逻辑

- `realtime_joint_control_example`：状态回调 + 独立控制线程 + 命令行修改共享整手控制帧。
- `homing_and_realtime_control_example`：在实时下发与透传归零之间显式暂停、切换和恢复。
- `impedance_control_example` / `impedance_position_sin_test`：展示单关节及整手阻抗字段的量化和周期更新。
- `canfd_socketcan_hand_control_example`：SDK 只处理协议，由示例的 SocketCAN 循环负责物理收发。
- `interpolated_joint_motion_example`：从最新反馈位置出发，以 10 ms 节拍执行五次平滑插值，按用户指定的浮点秒数到达目标；完成后继续读取下一段命令。

## 3. 延迟和频率的主要限制

### 3.1 固定的 10 ms 调度周期

这是应用目标值到总线下发的主要量化延迟：缓存刚错过一次采样时，约等待近 10 ms。周期目前写死在 `CommScheduler::SerialTask()`，配置中的串口 `timeout_ms` 并不控制调度频率。

建议将周期变成明确配置，例如 `control_period_us`，并设置合法范围。应用插值周期应读取相同配置，而不是各示例自行写死。

### 3.2 每帧固定等待 5 ms 才收包

固定等待让发送与接收不能重叠，并人为引入约 5 ms 的反馈可见延迟。若响应比 5 ms 更早，仍要等满；若响应更晚，本周期轮询可能读不到，要到下一周期才处理。

建议优先改成以下之一：

1. 单 I/O 线程使用串口可读事件或短超时阻塞等待，收到完整响应后立即解析，再按绝对时间发送下一帧；
2. 独立 RX 线程持续阻塞读取和拆帧，TX 调度线程只负责精确定时发送；
3. 平台允许时使用异步 I/O。协议解析器需要能持续接收分片并一次解析多帧。

### 3.3 串口和链路吞吐

实时控制载荷为 176 B，加 6 B 协议头和 4 B CRC 后约 186 B；1000000 baud、8N1 时，仅 PC 发送方向理论上约需 4.0 ms。整手状态约 158 B 级别，返回方向理论上约需 3.4 ms。再加掌板处理、收发切换和内部 11 关节轮询，100 Hz 已消耗链路周期的大部分预算。

因此不要仅把线程周期从 10 ms 改成 1 ms。应先用逻辑分析仪或串口时间戳测量请求起始、请求结束、响应起始、响应结束，再计算安全周期。提高波特率或使用 CAN FD、缩短帧、拆分控制与低频诊断数据，可能比单纯提高线程优先级更有效。

### 3.4 同步回调占用通信线程

`ProtocolHandler::UpdateHandStatus()` 在解析完成后直接调用用户回调。回调中的打印、文件写入或复杂计算会延长通信周期并制造抖动。

建议明确规定回调必须非阻塞；SDK 可选择只发布最新快照/无锁环形队列，由应用线程消费。实时线程内避免 `std::cout`、动态分配和不可控锁等待。

### 3.5 FIFO 命令挤占实时帧

实时模式中只要 `cmd_queue_` 非空，本周期就不会发整手控制帧。连续排入诊断或查询命令会让控制帧断流。`priority` 和 `wait_response` 字段虽然存在，但调度器没有使用。

建议把控制帧设为固定周期任务，诊断命令只使用剩余时隙，并设置每周期预算、优先级、超时和响应匹配。实时目标不应排成长 FIFO，应使用“latest value wins”的单槽/双缓冲语义。

## 4. 是否需要修改程序框架

### 目标 A：降低现有 100 Hz 的延迟和抖动

无需整体改框架。建议按顺序修改：

1. 加入 TX/RX 时间戳、周期超期计数、队列深度和丢帧统计。
2. 去掉固定 5 ms 休眠，改为事件驱动或持续 RX。
3. 状态回调与 I/O 线程解耦。
4. 调度周期参数化，并在超期时跳到下一个未来周期，避免追赶式连发。
5. 队列改为 `std::deque` 或有界环形队列，并真正实现优先级和响应等待语义。

### 目标 B：提高到 200 Hz 以上

保留 API、协议处理和传输适配器抽象，但通信执行模型需要升级：

- TX 定时线程和 RX 事件线程分离；
- 控制目标用原子快照或双缓冲；
- 诊断/配置流量与控制流量分级；
- 接口提供发送序号、状态时间戳、实际周期和丢帧信息；
- Windows 使用高分辨率等待并按需提升线程优先级，Linux 可评估 `SCHED_FIFO`、CPU affinity 与 `mlockall`；这些只能在链路带宽确认后做。

同时必须修改或确认掌板固件的控制周期和协议响应能力。如果掌板仍只在 100 Hz 消费 PC 目标，PC 提高发送频率只会增加排队和旧数据延迟。

### 目标 C：1 kHz 硬实时外环

通用 Windows/Linux 用户态 + 当前串口整手往返帧不适合作为严格 1 kHz 硬实时闭环。更合理的是把轨迹插值、限速和关键闭环下沉到掌板/关节固件，PC 低频发送带时间或速度约束的目标；或者采用实时系统和更高带宽、确定性的总线。

## 5. 已发现的问题与风险

### P0：`hand_control_example` 存在角度单位重复转换

SDK 的公共位置接口已经约定输入 degree，并在发帧前转换为 rad；但该示例正弦段把计算得到的 degree 又乘以 `pi/180` 后写入 `Hand_Control_t::position`。结果实际命令幅度约缩小 57.3 倍。示例状态回调也对已经逆映射为 degree 的 `status.position` 再乘 `180/pi`，显示值被放大约 57.3 倍。

应删除示例中的这两次手工转换，并统一文档说明：公共整手/单关节 API 和缓存状态均使用用户角度 degree，wire 数据才是 rad。

### P1：调度超期后可能追赶式连续发送

`SerialTask()` 每轮都执行 `time += 10 ms; sleep_until(time)`。当某轮发送、回调或系统调度耗时超过周期，目标时间已经在过去，后续循环会不休眠地连续运行，直到追上时间轴。这会产生突发帧和 CPU 峰值。

应检测 `now >= next_deadline`，记录 missed deadline，并把下一时刻推进到第一个未来周期；不要补发已经失效的控制采样。

### P1：停止设备后内部与外部运行状态容易不一致

`SG100Device` 公共对象和 `Impl` 分别维护 `is_running_`。内部 `StopSerialTask()` 会把 `Impl::is_running_` 置为 false，模式切换再恢复；公共标志只在公共 `Start()/Stop()` 更新。当前路径大多能恢复，但双状态源增加模式切换或异常早退后的状态漂移风险。

建议只保留一个设备生命周期状态，并把“设备已启动”与“调度线程正在运行”拆成两个命名明确的原子状态。

### P1：队列字段与实际语义不一致

`SG100_QueueCmd_t::priority` 和 `wait_response` 被赋值但未被调度器执行；所有命令均 FIFO，发送后无论字段值都固定等待 5 ms。调用方可能误以为优先级和响应等待已生效。

应实现这些语义，或在实现前从公共结构/文档移除，避免接口承诺与行为不一致。

### P1：实时队列可无界增长并饿死控制帧

两个命令队列都是无容量限制的 `std::vector`。生产速度高于每 10 ms 一条时会持续积压；实时模式积压期间不会发送缓存控制帧，旧命令延迟越来越大。

应设定容量和溢出策略。控制目标采用覆盖旧值；配置命令可拒绝、合并或返回队列满错误。

### P2：头部出队是 O(n)

`vector.erase(begin())` 每次移动剩余全部元素，队列变长后会扩大实时线程耗时。RS485、CAN FD 被动 TX 队列均有此模式。

应改为 `std::deque`、固定环形队列或 head index + 周期压缩。

### P2：RX 缓冲区满时直接丢弃已有数据

`RS485Adapter::PollReceive()` 在剩余空间为零时直接把 `rx_len_` 清零；被动注入也可能只接收输入的一部分却返回成功。高负载或异常分片时可能静默丢帧。

应先尝试解析/扩展有界环形缓冲，无法容纳完整输入时返回明确错误并累计 overflow 计数。

### P2：示例各自重复实现控制线程和周期常量

多个示例分别使用 10 ms、20 ms 或其他 sleep，且部分示例额外控制线程只是反复调用缓存更新 API。它们容易与 SDK 的真实发送周期不一致。

建议提供公共的周期配置/统计 API，以及可复用的轨迹工具；示例只演示业务逻辑。

### P2：Windows 串口名称转换会产生 C4244 警告并可能丢失字符

MSVC 19.51 编译 `src/impl/win.cc` 时在 `getPort()` 报告 C4244。当前实现直接用
`string(port_.begin(), port_.end())` 将 `std::wstring` 的 `wchar_t` 逐元素缩窄成
`char`，`setPort()` 也采用相反方向的逐元素扩展。普通 ASCII COM 名称通常可用，
但包含非 ASCII 字符的设备路径可能损坏。

应使用 Windows `WideCharToMultiByte()` / `MultiByteToWideChar()` 明确按 UTF-8 或
系统约定编码转换，而不是依赖迭代器窄化。

## 6. 插值示例的时间语义

`interpolated_joint_motion_example` 接受秒单位浮点数，最小 0.001 s，并用 `steady_clock` 计时。轨迹函数为五次 smoothstep：

`s(t) = 10t^3 - 15t^4 + 6t^5, t in [0, 1]`

命令目标在用户指定时刻被强制设置为终点。需要区分：这保证的是**主机目标插值的计划时长**，不保证机械关节在相同时刻无误差到达；实际跟踪还受位置环增益、输出限制、负载、总线周期和固件控制器影响。若要验证机械到达时间，应基于带时间戳的反馈定义位置误差阈值和稳定时间。

## 7. 推荐验证指标

改动通信框架前后至少记录：

- 应用目标更新时间 -> TX 开始时间；
- TX 结束 -> RX 首字节、RX 完整帧时间；
- 状态反馈周期的平均值、P95、P99、最大值；
- deadline miss、CRC error、RX overflow、队列满/队列深度；
- 控制序号对应的往返时延（需要协议或固件回显支持）；
- 不同波特率、不同回调负载和诊断流量下的对比。

只有这些数据稳定后，再决定是否提高频率或下沉插值到固件。
